## Cosa è stato fatto

### Aggiunto campo `pdb_name` a `scan_alert_log.sh`

Il DBA ha segnalato che l'alert log di un CDB contiene messaggi da tutti i PDB interni — era necessario identificare quale PDB ha generato ogni errore ORA-.

#### Scoperta tecnica: formato del log Oracle

Oracle 12c+ scrive il contesto PDB direttamente in ogni riga dell'alert log con il prefisso `PDBNAME(con_id):`:

```
VITAWFST(13):ORA-00060: deadlock detected while waiting for resource
AIMELA(20):ORA-1119 signalled during: CREATE TABLESPACE ...
PDB$SEED(2):Unified Audit record write ... failed due to ORA-942.
ORA-00800: soft external error, ...       ← nessun prefisso = CDB root
```

Il prefisso è sempre `^[A-Z][A-Z0-9_$#]*\([0-9]+\):` — nome PDB in maiuscolo + numero con_id tra parentesi + due punti.

#### Modifiche a `scan_alert_log.sh`

1. **Nuovo campo `pdb_name`** nell'output JSON: nome PDB (es. `"VITAWFST"`) oppure `null` per CDB root (riga senza prefisso).

2. **Aggregazione per coppia `(code, pdb_name)`**: lo stesso ORA- da PDB diversi genera item separati nell'array. Es. `ORA-00060` può apparire con `pdb_name: "VITAWFST"` e `pdb_name: "AIMELS"` come due righe distinte.

3. **Nuovo filtro `--pdb=NAME`** (opzionale, case-insensitive):
   - `--pdb=AIMELA` → solo errori del PDB AIMELA
   - `--pdb=CDB` → solo errori del container root (riga senza prefisso PDB)

4. **Fix: `ORA-0` è un success code Oracle**, non un errore. Oracle lo scrive come `Result = ORA-0` in certi messaggi diagnostici di DataPump e altri componenti. Corretta la regex da `ORA-[0-9]+` a `ORA-[0-9][0-9]+` (almeno 2 cifre).

5. **`sort -k3` invece di `-k2`** per il sort per count decrescente, perché è stato aggiunto `pdb_name` come secondo campo.
